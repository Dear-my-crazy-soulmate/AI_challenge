# 체험 문제 쓰기 지침 (v1)

대학 전공 과목의 **강의계획서**를 읽고, 그 과목의 한 주차에서 **일상 궁금증으로 이어지는 문제 1개**를 만든다.
읽는 사람은 그 학과에 "막연한 관심만 있는" 학생이다. 문제가 재미있어서 "이 학과에서는 이런 걸 배우네" 하고 느끼게 하는 것이 목표다.

## 하는 일 (반복)

1. 작업 목록 파일(`data/work/syllabus/2026/assignments/<id>.json`)의 다음 과목을 본다.
   ```
   cd <프로젝트 폴더> && PYTHONIOENCODING=utf-8 python -I scripts/syllabus/packets.py agent <작업 목록 파일 경로> 13
   ```
   과목마다 개요, 평가, 주차별 주제가 간추려져 나온다. `4~5주:`처럼 범위로 묶인 줄은 그 주차들의 주제가 같다는 뜻이다. 끝에 `…`가 붙은 줄은 80자에서 잘린 것이다.
2. **출력된 모든 과목**을 "문제 파일" 또는 "건너뜀 파일" 둘 중 하나에 넣는다. 어느 쪽에도 없는 과목은 다음 호출에서 다시 나온다.
   - 문제 파일: `data/drafts/quiz/_batches/<id>_<NNN>.json` (NNN은 001부터 호출마다 1씩 증가)
   - 건너뜀 파일: `data/drafts/quiz/_batches/skip_<id>_<NNN>.json` (건너뛴 과목이 하나도 없으면 만들지 않는다)
3. 파일은 **Write 도구**로 만든다(UTF-8). 한글과 특수문자가 있으니 셸 here-doc으로 만들지 않는다.
4. 검증하고, 문제가 나오면 그 파일만 고쳐서 0건이 될 때까지 반복한다.
   ```
   PYTHONIOENCODING=utf-8 python -I scripts/syllabus/build_questions.py --check <방금 만든 파일 경로>
   ```
5. 출력 끝이 `[left in this assignment: 0 of N]`이 될 때까지 1~4를 반복한다.

## 문제 파일 형식 (배열, 과목당 1개)

```json
[
 {
  "subjt_cd": "CSE203",
  "question": "책상 위에 자주 보는 책을 꺼내 두면 서가까지 왔다 갔다 하지 않아도 되죠. 컴퓨터(CPU)가 같은 아이디어로 속도를 높이는 방법은 무엇일까요?",
  "options": [
   "자주 쓰는 데이터를 CPU 가까이에 있는 작고 빠른 저장소(캐시)에 복사해 둔다",
   "모든 데이터를 하드디스크에만 두고 필요할 때마다 읽는다",
   "데이터를 쓸 때마다 인터넷에서 새로 내려받는다",
   "같은 계산도 매번 처음부터 다시 한다"
  ],
  "explanation": "CPU는 아주 빠른데 큰 저장 공간은 상대적으로 느려요. 그래서 자주 쓰는 데이터를 CPU 가까이의 작고 빠른 저장소에 복사해 두는데, 이걸 캐시(Cache)라고 해요. 책상 위 책장과 같은 역할이에요.",
  "flow": "🎓 컴퓨터구조는 4~6주차에 CPU가 명령을 어떻게 이해하는지(Instruction Set Architecture, MIPS Processor)를 배우고, 7~10주차 Pipelining으로 속도를 높이는 법을 거쳐, 14주차 Cache와 15주차 Virtual Memory로 메모리를 똑똑하게 쓰는 법까지 이어져요.",
  "evidence": {"week": 14, "topic": "Cache", "related_weeks": [6, 7, 15]}
 }
]
```

- `options`는 **서로 다른 4개이고, 첫 번째가 정답**이다. 정답 위치는 코드가 알아서 섞는다(번호를 적지 않는다).
- `explanation`은 본문만 쓴다. "정답 ②"를 쓰지 않는다(코드가 붙인다). 2~3문장, 해요체.
- `flow`는 `🎓`로 시작하는 한 문장(길어도 된다)이다. 이 과목이 어떤 순서로 이어지는지 **실제 있는 주차 번호**로 쓴다(`5주차`, `4~6주차`). 주차 번호는 출력에 나온 주차만 쓴다(시험·보강처럼 빠진 주차는 쓰지 않는다).
- `evidence.week`: 문제의 바탕이 된 주차. `evidence.topic`: 그 주차 주제에서 **그대로 옮긴 부분 문자열**(띄어쓰기·줄바꿈 차이는 괜찮다). 60자 안팎으로 짧게, `…`는 넣지 않는다. `related_weeks`: `flow`에서 언급한 다른 주차들(실제 있는 주차만).
- 같은 주제가 여러 주에 반복돼도 `evidence.week`는 그 범위의 첫 주로 쓴다.

두 번째 예(보기에 오답 설명을 붙이는 방식):
```json
{"subjt_cd": "AE352", "question": "눈 위를 걸을 때 넓은 눈신(설피)을 신으면 덜 빠져요. 건물 아래에 넓은 콘크리트 판(기초)을 까는 것도 같은 원리예요. 어떤 원리일까요?",
 "options": ["같은 무게라도 닿는 면적이 넓을수록 땅이 받는 압력이 줄어든다", "넓은 판이 건물의 무게를 줄여 준다", "넓은 판을 깔면 땅이 저절로 단단해진다", "넓은 판 아래의 공기가 건물을 받쳐 준다"],
 "explanation": "압력은 힘을 닿는 면적으로 나눈 값이에요. 같은 건물 무게라도 기초의 바닥 면적이 넓을수록 땅이 받는 압력이 작아져서, 땅이 버틸 수 있는 한계를 넘지 않게 돼요.",
 "flow": "🎓 철근콘크리트설계II는 1~5주차 기둥, 6~9주차 독립·복합·매트 등 여러 종류의 기초(Footings), 10~13주차 2방향 슬래브, 14~15주차 내력벽과 옹벽 설계로 이어져요.",
 "evidence": {"week": 6, "topic": "Footings: Wall Footings, independent Footings", "related_weeks": [1, 4, 9, 10, 15]}}
```

## 건너뜀 파일 형식 (객체)

```json
{"CSE406": {"name": "캡스톤디자인", "reason": "캡스톤: 학생이 프로젝트를 수행하는 과목"}}
```
`reason`은 한 줄. **억지로 만들지 않는다.** 아래 중 하나면 건너뛴다.
- 캡스톤·졸업논문·졸업작품·현장실습·독립/몰입심화·연구실 참여
- 가창·연주·안무·실기 평가, 작품 제작·워크숍·팀 프로젝트·발표·토론 위주
- 주별 내용이 비었거나 "스튜디오 실습"처럼 같은 말만 반복, 계획서에 개요와 주제가 거의 없음
- 법령·사례·이론 소개만 있고 일상 궁금증과 이어지는 구체 주제를 못 찾겠음
- 자신 있게 맞다고 말할 수 있는 사실을 찾지 못함

## 좋은 문제의 기준

- **일상의 장면이나 궁금증**으로 시작한다(예: 욕실에서 노래하면 왜 울릴까, 뒤로 가기는 왜 방금 본 페이지부터 돌아올까). 용어 정의를 묻지 않는다.
- 질문은 1~2문장, 끝은 "~일까요?" 같은 물음. 용어는 보기에서 처음 나오게 한다.
- 보기 4개는 **길이와 말투가 비슷**해야 하고(정답만 길거나 구체적이면 안 된다), 오답은 그럴듯하되 전공 지식이 있으면 분명히 틀렸다고 알 수 있어야 한다. 오답에 "X: …" 식으로 그 개념의 맞는 설명을 붙이는 방식을 써도 좋다.
- **사실이 정확해야 한다.** 확신이 없는 수치·역사·원리는 쓰지 않는다. 교과서식 단순화를 썼다면 `explanation`에 "~로 설명할 수 있어요"처럼 한정한다. 이 계획서에 없는 학교 정보(학점, 규정, 교수, 건물)는 쓰지 않는다.
- 문제의 주제는 반드시 그 주차 주제와 이어져야 한다. 계획서에 없는 개념을 끌어오지 않는다.
- 계산이 필요하면 코드로 확인한다(`python -c`), 머릿속으로 계산해 쓰지 않는다.
- 한 학과만의 문제가 아니라 과목 하나의 문제다. `depts:` 줄은 그 과목을 개설하는 학과 목록일 뿐이다.

## 지켜야 할 것

- 사람 이름(교강사, 조교 등), 이메일, 전화번호, 학번, 링크를 문제에 쓰지 않는다. 학술 개념 이름(예: 뉴턴의 법칙)은 괜찮다.
- 계획서 원문을 길게 옮기지 않는다. 근거 문구는 짧게.
- 문제 파일과 건너뜀 파일 **두 개 외에는 어떤 파일도 만들거나 고치지 않는다.** 다른 작업이 같은 폴더에 쓰고 있다. 스크립트도 고치지 않는다.
- `build_questions.py`는 반드시 `--check <파일>` 형태로만 실행한다(옵션 없이 실행하면 다른 작업의 결과를 덮어쓴다).
- git 명령(add, commit, push 등)은 실행하지 않는다.
- 끝나면 보고한다: 만든 문제 수, 건너뛴 수, 확신이 덜 가서 사람이 한 번 더 봐야 할 문제의 과목 코드(있다면), 100단어 이내.
